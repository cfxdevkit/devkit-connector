🎯 Core Database Purpose
The database serves as the central nervous system for both wallet modes, handling:

Security & Authentication: User verification and access control
State Management: Tracking all operations and their lifecycle
Audit Trail: Complete history for compliance and debugging
Performance: Caching and analytics for optimization
📊 Key Tables & Their Exact Usage
🔐 Security & Authentication Layer
sql
users                   → User accounts, 2FA, preferences
user_sessions          → JWT tracking, device management  
security_events        → Fraud detection, suspicious activity alerts
rate_limits           → Anti-abuse protection, DoS prevention
💰 Option A: Server-Managed Wallets
sql
server_wallets         → Encrypted mnemonics, derived addresses
server_wallet_access_log → Every wallet access for audit/security
encrypted_backups      → Disaster recovery, encrypted wallet backups
recovery_codes         → Emergency access codes
How it's used: When user calls loadServerWallet(), system:

Checks server_wallets for encrypted mnemonic
Logs access in server_wallet_access_log
Decrypts mnemonic in memory (never stored plain)
Creates temporary wallet instance for signing
🤝 Option B: User-Delegated Wallets
sql
delegation_sessions    → Active delegations, permissions, expiry
delegation_session_events → Every session change (renewal, config updates)
auto_approval_rules    → User's custom automation rules
rule_applications      → Track when/why rules triggered
How it's used: When user calls delegateUserWallet(), system:

Validates signature proving wallet ownership
Creates delegation_sessions record with permissions/limits
Stores user's custom auto_approval_rules
Tracks all events in delegation_session_events
⚡ Operations & Transactions (Both Options)
sql
wallet_operations      → Every operation (sign, send, balance check)
operation_state_changes → Audit trail of status changes
rule_applications      → Auto-approval decision tracking
Exact lifecycle tracking:

1. User requests transaction → wallet_operations (status: 'pending')
2. System checks rules → rule_applications (matched/rejected)
3. Auto-approved? → wallet_operations (status: 'approved')
4. Executing → wallet_operations (status: 'executing')
5. Blockchain confirms → wallet_operations (status: 'completed', transaction_hash)
📈 Analytics & Monitoring
sql
daily_statistics       → Aggregated metrics (transactions/day, volume)
user_analytics         → User behavior patterns, risk scoring
notifications          → Email/webhook delivery tracking

⚡ Performance Optimizations
Indexing Strategy:
Fast wallet lookups: idx_server_wallets_espace_address
Session queries: idx_delegation_sessions_expires_at
Operation history: idx_operations_created_at DESC
Security monitoring: idx_security_events_severity
Partitioning:
sql
-- Monthly partitions for high-volume tables
wallet_operations_2024_01  → January 2024 operations
wallet_operations_2024_02  → February 2024 operations
security_events_2024_01    → January 2024 security events
Caching Strategy:
Active sessions: Redis cache for fast delegation lookups
Balance queries: Cache for 5 minutes to reduce RPC calls
User preferences: Cache delegation configs
📋 Common Query Patterns
Dashboard Analytics:
sql
-- User's transaction summary
SELECT COUNT(*), SUM(CAST(operation_payload->>'value' AS BIGINT))
FROM wallet_operations 
WHERE user_id = $1 AND created_at > NOW() - INTERVAL '30 days';

-- Active delegations expiring soon
SELECT * FROM active_delegations 
WHERE minutes_until_expiry < 60;
Security Monitoring:
sql
-- Detect unusual activity
SELECT user_id, COUNT(*) as operation_count
FROM wallet_operations 
WHERE created_at > NOW() - INTERVAL '1 hour'
GROUP BY user_id 
HAVING COUNT(*) > 50;
Auto-Approval Analysis:
sql
-- Rule effectiveness
SELECT ar.rule_name, 
       COUNT(ra.*) as applications,
       COUNT(*) FILTER (WHERE ra.rule_result = 'approved') as approvals
FROM auto_approval_rules ar
LEFT JOIN rule_applications ra ON ar.rule_id = ra.rule_id
GROUP BY ar.rule_id, ar.rule_name;
🛡️ Security & Compliance Features
Audit Trail: Every action logged with:
Who (user_id, IP address)
What (operation type, parameters)
When (precise timestamps)
Why (auto-rule triggered, manual approval)
Result (success/failure, transaction hash)
Data Retention:
Operations: 7 years (compliance)
Security events: 3 years
Session data: 1 year after expiry
Analytics: Indefinite (aggregated)
Encryption:
Mnemonics: AES-256-CBC with unique IVs
Backups: Additional encryption layer
Signatures: ECDSA verification stored
This database design ensures complete traceability, regulatory compliance, and high performance while supporting both wallet operation modes seamlessly!
